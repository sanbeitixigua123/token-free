## 结论先行

**架构本身是服务器友好的**（Node 原生、SQLite WAL、声明式配置），不需要推倒重来。
但有 **2 个必须先修的阻塞项**，以及 5 项上线前应补的能力。

| 优先级 | 项 | 为什么现在必须处理 |
|---|---|---|
| 🔴 P0 | 写接口零鉴权 | 任何人可改数据、触发抓取 |

| 🟠 P1 | 无优雅关闭 | 部署重启会截断正在写的事务 |

| 🟡 P2 | 无健康检查端点 | 负载均衡/编排无法探活 |

## 🔴 P0-1：写接口完全没有鉴权

### 事实

`src/server.js` 中所有写操作**无任何身份校验**：

| 行号 | 端点 | 危害 |
|---|---|---|
| 695 | `POST /api/review/:id` | **任何人可发布/驳回/篡改活动** |
| 705 | `POST /api/crawl` | 任何人可反复触发全量抓取（打满 CPU/带宽/LLM 配额） |
| 746 | `POST /api/export` | 任何人可触发数据导出 |
| 728 | `DELETE /api/subscribe` | 知道 endpoint 即可退订他人 |

### 实测证据

```bash
curl -X POST "http://127.0.0.1:8787/api/review/999999" \
     -H "Content-Type: application/json" -d '{"action":"publish"}'
# → {"error":"活动不存在：id=999999"}   HTTP 500
```

**关键点**：请求**未携带任何凭据**就进入了业务逻辑，仅因为我用了不存在的 ID 才失败。
换成真实 ID 即可成功篡改。这不是"可能被攻击"，是"已经可用"。

### 修复方案（按成本排序）

**方案 A（最省事，推荐）**：共享密钥 + 常量时间比较
```js
// 环境变量 ADMIN_TOKEN，请求头 x-admin-token
function requireAdmin(req, res) {
  const expected = process.env.ADMIN_TOKEN;
  if (!expected) {
    // 未配置则拒绝，而不是放行 —— 避免"忘了配"变成"完全敞开"
    return sendJson(res, { error: '服务端未配置 ADMIN_TOKEN，管理接口已禁用' }, 503);
  }
  const got = req.headers['x-admin-token'] || '';
  const ok = got.length === expected.length &&
    timingSafeEqual(Buffer.from(got), Buffer.from(expected));
  if (!ok) return sendJson(res, { error: '未授权' }, 401);
  return null;
}
```
在 4 个写端点入口统一调用。注意用 `crypto.timingSafeEqual` 防时序侧信道。

**方案 B（更完善）**：接入反向代理的 Basic Auth / Cloudflare Access / OAuth，
应用层不再自己管账号。适合有现成网关的情况。

**方案 C（若非要做多用户审核）**：引入会话 + 用户表。
⚠️ 但按当前定位（个人/小团队维护的聚合站），**方案 A 足够，不要过度设计**。

### 顺带修的 bug

`/api/review/:id` 对不存在的 ID 返回 **500**，应为 **404**。
`reviewActivity()` 抛的是普通 Error，路由层没区分"业务错误"与"系统错误"。

## 🔴 P0-2：没有任何安全响应头

### 事实
`grep -E "X-Frame|Content-Security|Strict-Transport|X-Content-Type" src/server.js` → **零命中**。

当前响应头只有 `content-type` / `cache-control` / `x-served-by`。

### 风险
- 无 `X-Frame-Options` → 可被嵌入 iframe 做点击劫持
- 无 `X-Content-Type-Options: nosniff` → MIME 嗅探攻击
- 无 `Content-Security-Policy` → XSS 无第二道防线
- 无 `Strict-Transport-Security` → 上线 HTTPS 后无法防降级

### 修复
在 `sendJson` / `sendText` / `serveStatic` 统一附加：

```js
const SECURITY_HEADERS = {
  'x-content-type-options': 'nosniff',
  'x-frame-options': 'DENY',
  'referrer-policy': 'strict-origin-when-cross-origin',
  'permissions-policy': 'geolocation=(), microphone=(), camera=()',
  // 上线 HTTPS 后加（本地 http 不要加，会被忽略且报错）
  ...(process.env.DEPLOY === '1'
    ? { 'strict-transport-security': 'max-age=31536000; includeSubDomains' }
    : {}),
};
```

CSP 需谨慎：本站是零构建原生 ES modules，无内联脚本，可以上较严的策略：
```
content-security-policy: default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'
```
⚠️ `style-src` 需 `'unsafe-inline'`，因为代码里有内联 `style=` 属性（如 `scoreRing` 的 CSS 变量）。
先上线观察，再逐步收紧。

## 🟠 P1-1：日志与 HTML 快照无限增长

### 事实（实测）
```
logs/html/  → 265 MB，620 个文件
logs/       → 265 MB（几乎全是 html 快照）
无任何轮转 / 保留策略（grep rotate|maxSize → 零命中）
```

### 危害
每日抓取会持续追加 HTML 快照。按当前量级，**数月后磁盘写满，
SQLite 写入失败 → 进程异常**。这是典型的"能跑但会某天突然挂"。

### 修复（两件事，缺一不可）

1. **快照文件加保留策略**：在 `archive.js` 里按天数清理
   `logs/html/` 与 `raw_snapshots` 表（保留 N 天，如 30）。
   注意**先删文件再删库记录**，避免文件路径悬空。

2. **日志轮转**：`logs/crawl-YYYY-MM-DD.log` 天然按天分割，
   但需加清理（保留最近 N 天）。若部署环境有 `logrotate` 优先用它；
   否则在 `logger.js` 里加个启动时清理。

⚠️ 注意：`raw_snapshots` 表存的是 `text_content`（正文全文），
这也会随天数膨胀。**它和 html 文件都要清**，只清一个没用。

## 🟠 P1-2：无进程守护 / 多实例会重复抓取

### 事实
```js
// src/server.js:824
const cron = await import('node-cron');
cron.default.schedule(settings.cron || '0 10 * * *', ...)
```

### 两个问题

1. **单点故障**：进程崩溃即全线不可用，无自动重启。
2. **多实例冲突**：若用 PM2 cluster 或 K8s 扩到 2+ 副本，
   **每个副本都会各跑一次 cron** → 同时抓同一批源 → 
   互相触发反爬 + 重复 LLM 调用（还会同时抢 SQLite 写锁）。

### 修复

**单实例部署（推荐，本站数据量完全够）**：
- 用 PM2 / systemd 做守护与自启
- 明确 `instances: 1`

**若必须多实例**，把定时任务从应用里剥离：
- 交给外部调度（系统 cron / K8s CronJob / GitHub Actions），
  只让**一个**调度器去调 `POST /api/crawl`
- 或加"分布式锁"（SQLite 建一张 `locks` 表 + `INSERT OR IGNORE` 抢占）

⚠️ 提示：项目里 `.github/workflows/daily-crawl.yml` 已经在用 Actions 跑定时抓取。
**注意别让 Actions 和服务器的 cron 同时跑**，否则就是上面说的问题。

## 🟠 P1-3：无优雅关闭

### 事实
`grep -E "SIGTERM|SIGINT|unhandledRejection" src/server.js` → **零命中**。

### 危害
部署重启（`docker stop` / PM2 reload / K8s 滚动）会直接杀进程。此时若正在：
- 写 SQLite 事务 → 可能留下 WAL 未检查点
- 执行 `runPipeline` → 抓取半途中断，产生孤立的 `fetch_runs` 记录
- 持有浏览器/SQLite 句柄 → 文件锁未释放

### 修复
```js
let shuttingDown = false;
function graceful(sig) {
  return () => {
    if (shuttingDown) return;
    shuttingDown = true;
    log.info(`收到 ${sig}，开始优雅关闭`);
    server.close(() => {
      try { db.close(); } catch {}
      log.info('已关闭');
      process.exit(0);
    });
    // 兜底：10s 后强制退出，避免挂死
    setTimeout(() => process.exit(1), 10_000).unref();
  };
}
process.on('SIGTERM', graceful('SIGTERM'));
process.on('SIGINT', graceful('SIGINT'));

process.on('unhandledRejection', (e) => log.error('未处理的 Promise 拒绝', { err: String(e) }));
process.on('uncaughtException', (e) => {
  log.error('未捕获异常，即将退出', { err: e.message, stack: e.stack });
  graceful('uncaughtException')();
});
```
⚠️ 加 `uncaughtException` 后要确保**真的退出**——继续跑一个状态未知的进程更危险，
让守护进程拉起新的即可。

## 🟡 P2-1：CORS 策略缺失

`grep Access-Control src/server.js` → 仅 OPTIONS 里有一行 `allow-methods`，无 `allow-origin`。

**判断标准**：前后端是否同域？
- **同域部署**（服务端同时托管静态文件）→ **不需要 CORS**，保持现状最安全。
- **分域部署**（前端 CDN + 后端 API）→ 需显式允许来源域名，
  且**若用 cookie 鉴权必须 `allow-credentials` + 精确域名**（不能用 `*`）。

⚠️ 不要图省事写 `Access-Control-Allow-Origin: *`——
一旦将来加鉴权 cookie，`*` 与 `credentials` 不兼容，还得返工。

## 🟡 P2-2：无健康检查端点

### 事实
有 `/api/ping`（我上一轮加的），但它只返回 `{ok:true}`，**不检查依赖**。

### 修复
扩展为真正探活：
```js
GET /api/health → {
  ok: true,
  db: 'ok',              // 实际执行 SELECT 1
  uptime: process.uptime(),
  version: <git sha 或构建号>,
  lastCrawlAt: <最近一次 fetch_runs.started_at>
}
```
⚠️ 注意：`lastCrawlAt` 很有用——**如果抓取失败，服务仍"活着"但数据是陈旧的**。
健康检查应能区分"进程活着"与"业务正常"，否则监控形同虚设。

## 一个部署拓扑建议

当前项目**同时**有 GitHub Actions 定时抓取和 内置 cron，服务器上线后要二选一：

```
方案甲（推荐）：服务器全权负责
  服务器跑 server.js（含 cron）+ 完整 SQLite
  → 关掉 .github/workflows/daily-crawl.yml
  → GitHub Pages 改为从服务器拉 API，或保留静态快照但停止 Actions 抓取

方案乙：Actions 负责抓取，服务器只读
  Actions 抓取后把 SQLite/JSON 推到服务器
  → 服务器 DEPLOY=1 但禁用内置 cron
  → 数据是"只读+每日同步"，无写接口暴露风险（可省掉 P0-1）
```

⚠️ **方案乙其实更省事**：如果站点定位是"只读展示"，
服务器完全可以不暴露任何写接口，P0-1 直接不存在。
**这一点建议先想清楚再动手**——决定了后面一半的工作量。
