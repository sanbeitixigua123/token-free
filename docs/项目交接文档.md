## 四、架构

### 4.1 四层数据模型（本项目的核心设计）

```
Provider（厂商）
   ↓
Endpoint（端点）  ← 长期有效的免费额度政策，"常态"
   ↓
Model（模型）     ← 能力载体
   ↓
Activity（活动）  ← 限时促销，"限时"
```

**为什么要分端点和活动**：这是本项目最重要的抽象。
「智谱常年给新用户 2000 万 token」是**端点**（稳定，可长期依赖）；
「国庆三天送 1 亿」是**活动**（限时，会过期）。
混在一起会让"过期"逻辑污染稳定数据。

### 4.2 六层流水线

```
discover（发现）→ fetch（抓取）→ extract（抽取：规则 + LLM）
→ normalize（归一化）→ validate（校验）→ persist（落库）→ notify（通知）
```

置信度三档分流：`auto_ok`（自动发布）/ `pending`（人工审核）/ `reject`（驳回）。

### 4.3 双模式前端

零构建，原生 ES modules + hash 路由。数据层自动切换：

| 模式 | 数据来源 | 触发条件 |
|---|---|---|
| **API 模式** | `/api/*` 实时查库 | 服务端响应带 `x-served-by: token-free-api` |
| **静态模式** | `public/data/*.json` | 无该头（如 GitHub Pages） |

前端靠探测 `manifest.webmanifest` 的响应头判断模式。
顶部会显示「静态只读版」提示条。

## 七、部署（方案 A）

服务器同时托管前端 + API，抓取由服务器内置 cron 负责，Pages 作降级快照。

### 三条硬约束 ⚠️

1. **必须持久化 `data/`** — 不挂卷 = 每次空库 = 丢掉增量优化，白耗 LLM 配额
2. **只能单实例** — 多副本会因内置 cron 各抓一次（互相触发反爬 + 重复耗配额）
3. **必须设 `ADMIN_TOKEN`** — 不设则管理接口返回 503（设计为「禁用」而非「放行」）

### 部署方式

```bash
# Docker（推荐）
docker build -t token-free .
docker run -d -p 8787:8787 \
  -e ADMIN_TOKEN=<生成的随机串> \
  -v token-free-data:/app/data \
  -v token-free-logs:/app/logs \
  --restart unless-stopped token-free

# PM2
ADMIN_TOKEN=<...> pm2 start ecosystem.config.cjs && pm2 save && pm2 startup

# systemd
sudo cp deploy/token-free.service /etc/systemd/system/
sudo systemctl enable --now token-free
```

### 环境变量（见 `.env.example`）

| 变量 | 必填 | 说明 |
|---|---|---|
| `ADMIN_TOKEN` | ✅ | 管理接口令牌 |
| `DEPLOY=1` | ✅ | 绑 0.0.0.0 + 启用 HSTS |
| `PORT` | | 默认 8787 |
| `CRON=0` | | 关闭内置定时（外部调度时用） |
| `TOKENFREE_LLM_API_KEY` | | LLM 抽取，不配则纯规则 |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | | Web Push |

### 管理接口（需 `x-admin-token` 头）

| 端点 | 作用 |
|---|---|
| `POST /api/review/:id` | 发布/驳回/修订活动 |
| `POST /api/crawl` | 手动触发抓取 |
| `POST /api/export` | 导出静态数据 |
| `DELETE /api/subscribe` | 退订 |

### 监控

`GET /api/health` — 返回 `db` / `uptime` / `memMB` / `lastCrawlAt` / `lastCrawlStatus` / `cronEnabled`。
**注意看 `lastCrawlAt`**：抓取失败时服务仍然「活着」，只看进程存活的监控形同虚设。

## 九、踩过的坑（交接中最有价值的部分）

### 9.1 数据模型类

| 坑 | 说明 |
|---|---|
| **`activities` 表没有 `status` 列** | 状态由视图 `v_activities` 实时派生。查状态必须用视图，用表会报 `no such column` |
| **能力计数有三个口径** | `endpointCount` / `modelCount` / `activityCount`，**不可混用**。模型库页用 modelCount，端点库页用 endpointCount。混用会导致「显示 7 个点进去只有 3 个」 |
| **一个 JOIN 表达两种多对多会笛卡尔积** | 曾导致计数恒为 1。改成分能力独立查询 + JS 合并 |
| **`endpoint_id` 等字段要看视图** | 这是本项目第二次踩「表 vs 视图」的坑 |

### 9.2 前端类

| 坑 | 说明 |
|---|---|
| **`#app` 就是 `.app-main`** | `$app.innerHTML = ...` 会整体替换。任何需跨路由常驻的 UI 必须是 `<main>` 的**兄弟节点**，放进去会被冲掉 |
| **模式探测不能靠 404** | 浏览器对任何 4xx 都会打 console.error，JS 无法抑制。改为探「两模式都存在的文件」+ 自定义响应头区分 |
| **验证脚本断言要跟实现同步** | 实现从「动态创建元素」改为「切 hidden」后，断言必须从存在性改为可见性，否则**脚本会谎报回归** |
| **`waitUntil:'networkidle'` 必然超时** | 改用 `'load'` + `waitForFunction(骨架消失)` |

### 9.3 LLM 类（本会话最贵的两条经验）

| 坑 | 说明 |
|---|---|
| **`/models` 列得出来 ≠ 可调用** | Gemini 和智谱都踩了：列表能返回，实际调用报「已下线」或「余额不足」。**必须实发一次请求验证** |
| **GLM 思考模式会劣化抽取** | 实测 A/B：开思考 7.8s + `title` 返回 null；关思考 0.65s + `title` 正确。**不是"慢但更准"，是又慢又不准**。已在请求体固定 `thinking:{type:'disabled'}` |
| **免费层必须节流** | 不节流时 18 秒内 39 次 429，当轮仅 1 个源成功。加 3s 间隔后 0 次 429、发现条数 5→39 |
| **429 是「软失败」** | 不触发凭据熔断，日志只有 WARN。**只看"无凭据告警"会误判一切正常**，必须看成功计数 |
| **凭据排障要分离测三类端点** | 认证 / 元数据 / 推理。只测一类就下结论会导致方向性错误（曾错误断言「AQ. 前缀必然不可用」，实测推翻） |

### 9.4 环境与工具

| 坑 | 说明 |
|---|---|
| **git push 必须指定助手** | `git -c credential.helper=manager push origin main`（`~/.gitconfig` 里有个空的 `credential.helper=` 会清掉系统配置） |
| **Playwright 自带 Chromium 下载会卡死** | 20 分钟无进展。改用 `chromium.launch({ channel:'chrome' })` 驱动本机 Chrome，零下载 |
| **ESM 不认 NODE_PATH** | 浏览器验证脚本必须放在 `C:/Users/14635/.workbuddy-ai/binaries/node/workspace/` |
| **`src/` 下任何改动都要重启服务** | 内存里是旧代码，曾因此多绕一圈 |
| **Windows 中文路径会让 MRS 工程加载失败** | 与本项目无关，但同机 CH32 开发时注意 |
